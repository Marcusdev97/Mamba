# Notion CRM v1

> Schema version: 2 · Product structure remains CRM v1 · Source of truth: `campaign-app/domain/notion-crm-schema.mjs`

Notion is Mamba's online CRM and human tracking interface. SQLite remains the runtime
source for messages, send jobs, recovery state, idempotency, sync cursors and immediate
Campaign results.

## Databases

The v1 CRM contains exactly eight databases:

1. `Mamba CRM | Customers`
2. `Mamba CRM | Project Leads`
3. `Mamba CRM | Follow-up Tasks`
4. `Mamba CRM | Sales Opportunities`
5. `Mamba CRM | Campaigns`
6. `Mamba CRM | Campaign Runs`
7. `Mamba CRM | Conversation Summaries`
8. `Mamba CRM | AI Lead Reviews`

Legacy Blast Leads, Ads Leads, Recycle Leads, Campaign Templates and Images remain
separate integrations during migration. The provisioner writes CRM IDs under
`notion_config.json -> crm.databases` and does not replace legacy database IDs.

## Stable IDs and relations

Every database uses its stable business ID as the title property. Customer IDs are
derived deterministically from the SQLite contact key without copying the raw phone into
the title. Relations are created only after all eight database IDs are known:

- Project Leads → Customers, Campaigns
- Follow-up Tasks → Customers, Project Leads
- Sales Opportunities → Customers, Project Leads
- Campaign Runs → Campaigns
- Conversation Summaries → Customers, Project Leads
- AI Lead Reviews → Customers, Project Leads

Re-running provisioning discovers exact database titles and configured IDs before any
write. Existing property type or relation conflicts stop apply; the system never silently
changes a conflicting field type.

## Field ownership

The complete ownership manifest is generated by `crmFieldOwnership()`.

- `human`: Notion edits may be imported into SQLite after validation.
- `system`: SQLite/outbox owns the value; Notion is a mirror.
- `notion`: Notion-generated metadata such as `last_edited_time`.

Human fields include names, owner, budget, purpose, areas, timeline, objections, sales
stage, next action/follow-up, appointment/opportunity details and human notes. System fields
include stable IDs, raw send evidence timestamps, Flow state, run counts, sender/device,
deduplication and sync status.

When SQLite and Notion changed the same human field after the last successful sync,
`Sync Status` becomes `Conflict`; neither side silently overwrites the other. When only
Notion changed, the sync service returns an approved human-field patch for the SQLite
repository to validate and apply.

## Privacy

Never copy complete message payloads, API credentials, identity/bank documents, sync
cursors, run recovery state or deduplication keys into Notion. Conversation Summaries may
contain short latest-message excerpts and an explicit summary period, but raw messages
remain in SQLite.

## Provisioning

Dry-run is the default and performs no writes:

```bash
node scripts/maintenance/provision-notion-crm.mjs --dry-run
```

Apply requires a dedicated `Mamba | CRM Hub` page shared with the Mamba integration,
the page ID, and an explicit confirmation token:

```bash
node scripts/maintenance/provision-notion-crm.mjs \
  --apply \
  --parent-page-id <CRM_HUB_PAGE_ID> \
  --confirm CREATE_NOTION_CRM_V2
```

The maintenance provisioner creates database schemas and relations but does not create
saved views. Establish the views through an authorised Notion connector or the Notion UI,
verify their filters, then set `crm.viewsRequireManualSetup` to `false`. Re-running the
provisioner preserves that verified state.

The v1 views use these meanings:

- Home: due open tasks, human-takeover replies, hot/qualified project leads, appointment
  calendar, Booking/SPA board, and Customer sync conflicts/errors.
- Customers: Active, No Reply (active with no inbound reply), Warm (qualified or later),
  Snoozed (active with a planned next follow-up), Stop, Won, and Lost.
- Opportunities: one view for each active sales stage plus At Risk, defined as an active
  opportunity without a next follow-up.

## Rollout

1. Create and share a dedicated CRM Hub page.
2. Run dry-run and require `conflict: 0`.
3. Apply once with explicit confirmation.
4. Re-run dry-run; all eight databases must be `READY`.
5. Create and verify the Home, Customers and Opportunities views.
6. Run a single test customer twice and verify one page only and one Project Lead relation.
7. Test a Notion-only human edit, a two-sided conflict and Notion offline outbox recovery.
8. Migrate legacy Blast Leads into Customers + Project Leads through a separate dry-run;
   do not bulk-move production rows during an active LIVE Campaign.
